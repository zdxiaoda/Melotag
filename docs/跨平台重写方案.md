# MusicTag 跨平台重写方案（Windows / Linux / Android）

> 前提：按上一份《功能清单与复刻方案》的行为规格**重写**，不复用原程序的二进制、图标与文案。
> 目标：一套 C# 核心 + 一套 UI，桌面（Win/Linux）与 Android 共用；平台差异只留在很薄的 head 层。

---

## 0. UI 外观决策：Material Design 3

如果 MD3 是**硬性产品要求**（而不是"看起来像 Material"），它会直接改变技术选型。2026-10 的实际情况：

| 事实 | 影响 |
|---|---|
| `Material.Avalonia` 是社区维护的 **MD2** 实现，README 自述仍处 alpha | 不是 MD3，且不能指望它升级 |
| `Material3.Avalonia`（klorman）是个人 WIP 项目，"核心系统基本就位" | 不能作为生产依赖，最多当参考 |
| **官方 MD3 实现只有 Compose（Jetpack Compose Material3）**；Compose Multiplatform 通过 `org.jetbrains.compose.material3`（基于 Jetpack Material3 1.4.x）在 Desktop/Android/iOS 共用 | 想要"官方 MD3 + 一套 UI 三端"，Compose Multiplatform 是唯一路径 |
| M3 Expressive（2026）在 Compose 侧已有实验性 `MaterialExpressiveTheme` | MD3 仍在演进；自建主题要持续跟 |

### 两条路线

**路线 A：Avalonia + 自建 MD3 设计系统**（保留 C# 与 TagLib#）

- 要做的事：HCT 色板与 color roles（可移植 material-color-utilities）、state layer、elevation/tonal surface、shape scale、typography（Roboto + Material Symbols）、以及约 18 个组件的 ControlTheme。
- 可复用：`Material.Avalonia` 当结构底子（按钮/输入框/对话框骨架）、`Material.Icons.Avalonia` 图标、Material Symbols 字体。
- 成本：3–5 周（含打磨），之后**长期自己维护**；Android 动态取色需要写平台服务（Monet/壁纸取色 → 生成 tonal palette）；ripple、edge-to-edge、insets 都要自己做。
- 保真度：能到 85–90%，细节（动效曲线、Expressive 新组件、平台手感）会持续落后。

**路线 B：Compose Multiplatform**（官方 MD3，放弃 C# 核心）

- 一套 Kotlin + Compose 覆盖 Windows / Linux / Android，`material3` 直接用官方实现，Android 上动态取色（Material You）免费获得，M3 Expressive 可开实验开关。
- 代价：
  - 核心要用 Kotlin 重写（模板/正则/歌词/合并这些逻辑约 3–5k 行，有规格文档的话是机械劳动）。
  - 标签引擎换成 **jaudiotagger**（纯 Java，MP3/FLAC/OGG/MP4/WAV/AIFF/WMA 等覆盖好；APE/DSD 不完整）或 **TagLib C++ 的 JNI 封装**（格式覆盖与原程序一致，代价是每平台编 .so/.dll）。
  - 桌面侧是 JVM：安装包 60–100 MB、内存基线更高；数据表格、多选、键盘导航、系统菜单仍要自己写。
- 收益：UI 不再是一项长期负债，Android 体验与原生一致。

### 建议的判据

| 你的权重 | 选 |
|---|---|
| Android 是一等公民 + MD3 必须"像官方" + 接受 Kotlin | **B（Compose Multiplatform）** |
| 桌面大量表格/键盘操作优先 + 想复用 C# 与 TagLib# + MD3 只要"风格一致" | **A（Avalonia + 自建 MD3）** |
| 两边都想要 | 先做 3 天双栈 spike：同一屏（列表+编辑面板+一个对话框）各做一版再定 |

> 无论哪条路：**MD3 没有数据表格组件**。这个软件的主界面是"上万行的表格 + 行内编辑 + 多选 + 列拖拽"，这部分永远要自建；MD3 只覆盖外壳（AppBar、导航、按钮、表单、对话框、Snackbar）。

## 0.5 主题库选型（不要求 MD3）

Avalonia 的"好看"主要来自第三方主题库 + 自己的排版纪律。当前可选（2026）：

| 库 | 风格 | 适合本软件？ | 备注 |
|---|---|---|---|
| **Semi.Avalonia** | Semi Design（现代、克制、中性灰 + 单一强调色） | **首选** | 控件覆盖全，自带 DataGrid/TreeDataGrid 样式包，亮/暗双主题，中文社区活跃，MIT |
| **FluentAvalonia** | WinUI 3 / Fluent | 次选 | 桌面质感最好、控件最全（NavigationView/TabView/ContentDialog），但三端都像 Windows |
| **Ursa.Avalonia** | 企业级 LOB（表单、对话框、导航齐全） | 可选 | 适合"工具感"，视觉偏传统后台 |
| **ShadUI** | shadcn/ui（细边框、圆角、zinc 中性色） | 可选 | 现代开发者工具风，组件较少，表格样式需自己补 |
| **SukiUI** | 玻璃拟态/大圆角/动效多 | **不建议** | 展示型应用很好看，但密集表格 + 大量动效会拖累性能与信息密度 |
| **Citrus.Avalonia** | 简洁多配色 | 小项目 | 控件少 |
| **CherylUI** | 移动端风格 | Android 壳可参考 | 桌面不适用 |

**推荐组合**：`Semi.Avalonia`（含 DataGrid/TreeDataGrid 样式）+ Avalonia 官方 **TreeDataGrid** 作为文件列表 + `Material Symbols` 或 `Phosphor` 图标 + `Inter` / `Noto Sans SC` 字体 + 自定一套中性色板。

选型纪律：

- **表格组件是主界面**，先验证"主题库对 TreeDataGrid/DataGrid 的样式支持"，这比按钮好不好看重要得多。没有现成样式就自己写（约 200 行 ControlTheme）。
- **密度优先**：行高 28–32px，提供"紧凑/舒适"两档；MD3/Fluent 默认的 40–48px 行高对批量编辑工具太浪费。
- **暗色从第一天做**（`ThemeVariant` 双套色板），否则后期返工。
- **Android 不要复用桌面 XAML**：同一套 ViewModel + 设计 token，另做一个移动壳（底部导航 + FAB + 底部抽屉），桌面用三栏（目录树 / 列表 / 编辑面板）。

## 1. 结论（先给答案）

**Avalonia + 纯托管 TagLib# + SQLitePCLRaw + ImageSharp + OpenCC.NET**，一个 `Core` 库、一个 `UI` 库、两个 head（Desktop / Android）。

> 前提：Material Design 3 只作为"视觉风格"而非逐像素规格。若 MD3 是硬指标，先按 §0 在 Avalonia 自建主题与 Compose Multiplatform 之间做取舍。

理由：

- Avalonia 11 官方支持 **Windows、Linux、macOS、Android、iOS**，XAML 一套 UI 三端复用，是"桌面 + Android 同构"目前唯一成熟的 C# 方案。
- MAUI 不支持 Linux（社区版不可靠），直接排除。
- Flutter / Tauri / Electron 要求放弃 C# 生态，TagLib#、SQLite、ImageSharp、OpenCC 全部要换实现或走 FFI，得不偿失。
- 原程序的标签引擎本来就是 TagLib 分支，用 TagLib# 语义最接近，且**纯托管、无需为三端编译原生库**。

唯一需要留后门的点：**DSF/DFF（DSD）写入**。TagLib# 上游对 DSD 支持不完整。做法是把 `ITagStore` 抽象出来，先用 TagLib# 覆盖 90% 格式，之后可选接入官方 TagLib C++（一套 C ABI 薄壳，Win/Linux 用 CMake，Android 用 NDK）补齐 DSD。

## 4. 六个必须做对的抽象

### 4.1 文件访问：`IFileSystem` + TagLib 的 `IFileAbstraction`

Android 不能拿任意路径读写，必须走 SAF（`content://` URI）。TagLib# 支持流式抽象，正好对上：

```csharp
public interface IFileHandle : IDisposable
{
    string DisplayPath { get; }      // 展示用："root/album/01.flac" 或 content URI 的可读形式
    string? PhysicalPath { get; }    // 桌面才有；Android 为 null
    long Length { get; }
    DateTimeOffset LastWriteTime { get; }
    Stream OpenRead();
    Stream OpenWrite();               // Android 需 ContentResolver.OpenOutputStream("wt")
    void ReplaceWith(IFileHandle source); // 原子替换：桌面 File.Replace，Android 重写目标流
    IFileHandle? GetSibling(string fileName); // .lrc / 图片同目录操作
    string Extension { get; }
    string FileNameWithoutExtension { get; }
}

public interface IFileSystem
{
    Task<IReadOnlyList<IFileHandle>> EnumerateAsync(IFileHandle folder, EnumOptions opts, CancellationToken ct);
    Task<IFileHandle?> PickFolderAsync();
    Task<IFileHandle?> PickFileAsync(string[] extensions);
    Task<bool> DeleteAsync(IFileHandle file);
    Task<IFileHandle> RenameAsync(IFileHandle file, string newName);
}
```

TagLib# 侧：

```csharp
sealed class HandleAbstraction(IFileHandle h, string? temp) : File.IFileAbstraction
{
    public string Name => h.DisplayPath;
    public Stream ReadStream  => h.OpenRead();
    public Stream WriteStream => h.OpenWrite();
    public void CloseStream(Stream s) => s.Dispose();
}
```

> 关键点：**写标签一律"读到临时文件 → 改 → 原子替换"**。Android 上 `File.Replace` 不存在，`ReplaceWith` 用"打开目标输出流覆盖 + 校验长度"实现，并保留一份 `.bak` 直到成功。

### 4.2 标签引擎：`ITagStore`，TagLib# 先行

```csharp
public interface ITagStore
{
    TagFieldSet Read(IFileHandle file);
    void Write(IFileHandle file, TagFieldSet tags, TagWriteOptions options);
    IReadOnlyList<Picture> ReadPictures(IFileHandle file);
    void WritePictures(IFileHandle file, IReadOnlyList<Picture> pictures);
    bool CanHandle(IFileHandle file);   // 按扩展名 + 少量 magic 探测
}
```

DSD 补齐路径（可选）：官方 TagLib C++ 2.x 编成 `libmusictag_native`，暴露 10 个左右的 C 函数（open/read_tags/write_tags/read_picture/close），三端各编一次；`NativeTagStore` 实现同一接口，按引擎能力路由。**不要在第一天做这件事**。

### 4.3 技术参数：先 TagLib，后 MediaInfo

原程序用 MediaInfo 补格式/时长/比特率/采样率/声道。跨平台取舍：

- **首选**：TagLib 的 `Properties` 已经给了 duration/bitrate/samplerate/channels，零原生依赖。
- 需要更细（如"无损/有损"、编码 profile）时，可选接 `libmediainfo`：Linux 有包、Windows 有 DLL、Android 需自编（.so 体积 ~8 MB）。把它做成 `IAudioInfoProvider` 的第二个实现，按平台启用。

### 4.4 持久化：SQLite 一律用 `SQLitePCLRaw.bundle_e_sqlite3`

三端都能用，无系统依赖。Android 上历史表的主键不要用绝对路径：

```sql
CREATE TABLE tag_history (
  serial     TEXT PRIMARY KEY,
  root_id    TEXT NOT NULL,   -- 桌面：盘符/根目录 ID；Android：SAF tree URI 的持久化 ID
  rel_path   TEXT NOT NULL,   -- 相对 root 的路径（统一 / 分隔）
  size       INTEGER,         -- 校验用，避免 URI 复用导致错配
  mtime      INTEGER,
  created_at TEXT NOT NULL,
  payload    TEXT             -- JSON：字段 + 歌词/封面备份的相对路径
);
CREATE UNIQUE INDEX ux_history ON tag_history(root_id, rel_path);
```

设置存 JSON：Windows `%APPDATA%`、Linux `$XDG_CONFIG_HOME`、Android `Context.FilesDir`；用 `IAppPaths` 抽象取目录。

### 4.5 图像：ImageSharp，不要 `System.Drawing`

`System.Drawing.Common` 在 .NET 6+ 只支持 Windows。封面缩放/JPEG 质量重编码全部走 `SixLabors.ImageSharp`（Android/ARM 正常）。

### 4.6 平台差异服务：一个 `IPlatformService`

```csharp
public interface IPlatformService
{
    SafeNamePolicy NamePolicy { get; }           // 见 §5.1
    Task ShareFileAsync(IFileHandle file);       // 桌面：打开资源管理器定位；Android：ACTION_SEND
    void KeepScreenOn(bool on);
    bool BackgroundJobsSupported { get; }        // Android 需要前台服务
    Task RunInBackgroundAsync(Func<CancellationToken, Task> work, string title);
}
```

**Android 特有**：批量保存/批量匹配这类长任务必须放进 **前台服务**（`ForegroundService` + 通知）或 WorkManager，否则切后台会被系统杀掉。桌面直接 `Task.Run` + 进度条即可。

## 5. 跨平台行为差异（必须在实现里显式处理）

### 5.1 文件名合法化

同一个"安全文件名"策略在三个平台不一样：

| 规则 | Windows | Linux | Android (SAF/FAT) |
|---|---|---|---|
| 非法字符 | `\ / : * ? " < > \|` + 控制字符 | 仅 `/` 与 NUL | 同 FAT：`\ / : * ? " < > \|`，且部分设备额外限制 |
| 保留名 | `CON PRN AUX NUL COM1-9 LPT1-9`（含带扩展名） | 无 | 视底层文件系统 |
| 结尾点/空格 | 不允许 | 允许 | 通常不允许 |
| 大小写 | 不敏感 | 敏感 | 视文件系统 |
| 长度 | 路径 260（需 long path 支持） | 255 字节/段 | 视文件系统 |

实现：`SafeNamePolicy` 每个 head 注入一份规则；重命名前做**冲突检测**，冲突时按 `title (2).ext` 递增，并把"是否大小写不敏感比较"做成策略参数。

### 5.2 路径与编码

- 内部统一用 `/` 分隔的相对路径 + `root_id`，展示时再转平台风格（避免模板里出现 `\`）。
- 文件名/标签字符串统一 **NFC** 归一化后再比较与写盘（Android/Linux 常为 NFC，Windows 也 NFC，但外部来源可能是 NFD）。
- 排序用 `StringComparer.InvariantCulture` 的明确策略，不要依赖当前区域设置（Linux 上 `zh-CN` 未必装了 ICU 数据）。

### 5.3 权限与沙箱

- **Linux**：AppImage 无沙箱、直接读写；Flatpak 需要 `--filesystem=home` 或走 XDG 门户（portal），否则用户选的目录拿不到真实路径 → `IFileHandle` 必须能只靠 URI/句柄工作（和 Android 同一套抽象）。
- **Android**：`MANAGE_EXTERNAL_STORAGE` 不要用（Google Play 会拒）。用 `ACTION_OPEN_DOCUMENT_TREE` 拿持久化 URI 权限，逐目录授权。
- **Windows**：不需要管理员；长路径用 `\\?\` 前缀或 app.manifest 开 `longPathAware`。

### 5.4 网络

- Android 默认禁止明文 HTTP；原程序有 `http://` 源（Last.fm、MusicBrainz、CoverArtArchive、ViewLyrics）。**统一改 HTTPS**（这些源都支持）。
- 每源独立 `HttpClient` + `SocketsHttpHandler`（连接池复用、每源并发限制、`Polly` 重试）。
- Android 加 `INTERNET` 权限；考虑加上"仅 Wi-Fi 下载封面/歌词"选项（移动流量友好）。

### 5.5 生命周期

| 场景 | 桌面 | Android |
|---|---|---|
| 批量任务 | 后台线程 + 进度条 | 前台服务 + 通知进度 + 可取消 |
| 数据库 | 单进程直连 | 单进程直连（应用内），注意 `WAL` 与并发写串行化 |
| 配置 | 即时落盘 | `onPause` 时落盘（进程可能被杀） |
| 大列表 | 虚拟化 ListView | 必须虚拟化 + 分页加载，避免一次渲染上万项 |

## 6. 推荐实施顺序（每步都能跑）

1. **Core 先行（1 周）**：把《功能清单》里的模型、模板/正则引擎、歌词流水线、合并策略写成纯托管库 + 单测。**不碰 UI、不碰文件系统**。
2. **Tags 层（1 周）**：TagLib# + `IFileHandle`，在桌面用真实样本跑往返测试；`CanHandle` 覆盖 13 种格式。
3. **Desktop head（1–2 周）**：Avalonia 主窗体、列表虚拟化、读取/保存、批量改名。此时已经可用。
4. **Storage（3–5 天）**：SQLite 历史 + 撤销 + 设置 JSON。
5. **在线源（1–2 周）**：先做 2 个合规源（MusicBrainz + Cover Art Archive），接口定型后再加 Last.fm/iTunes。
6. **Android head（2–3 周）**：SAF `IFileSystem` 实现 → 同一 UI 编译到 Android → 前台服务承载批量任务 → 权限流程。
7. **可选增强**：原生 TagLib 后端补 DSD；MediaInfo 可选；简繁转换；三语。

第一周结束时应能回答一个关键问题：**TagLib# 对目标格式的写入覆盖是否够用**。如果用户群大量使用 DSF/DFF，就把"原生 TagLib 后端"提前到第 2 步，其余不变。

## 8. 上架与分发注意

- **Google Play**：音乐标签编辑属于正常工具类；但"读取用户全部音乐文件"需要 `READ_MEDIA_AUDIO`（Android 13+），并要在商店说明里写清用途。禁止 `MANAGE_EXTERNAL_STORAGE`。
- **Flatpak/Flathub**：需要在 manifest 里声明文件系统权限；如果坚持最小权限，就要完全依赖 portal 句柄（和 Android 共用抽象，收益很大）。
- **Windows**：可签名分发；不签名会触发 SmartScreen。
- **协议**：MusicBrainz 要求明确 User-Agent 且 ≤1 req/s；Last.fm 需要自申请 API key；iTunes Search 有调用频率限制。把这些做成可配置项，别硬编码。
